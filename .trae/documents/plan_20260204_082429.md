# Analysis of Interface Latency (`/analyze`)

Based on the code analysis of `backend/api/v1/analysis.py` and its dependencies, here is the breakdown of the current performance bottlenecks and a plan to optimize it.

## 1. Latency Analysis (Static Analysis)

The current implementation is **fully synchronous and blocking**, which severely impacts performance and concurrency. Although the API endpoint is `async def`, it calls blocking synchronous functions.

| Stage | Operation | Estimated Time | Nature | Bottleneck |
|-------|-----------|----------------|--------|------------|
| **1. Preprocessing** | Regex & String Ops | < 10ms | CPU Bound | Negligible |
| **2. Rule Engine** | LanguageTool Check | 100ms - 500ms | CPU/IO Mixed | Blocking Main Thread |
| **3. LLM Engine** | Zhipu AI API | **5s - 15s** | Network I/O | **Critical** (3 sequential blocking calls) |
| **4. Merging** | Diff & Merge Logic | < 10ms | CPU Bound | Negligible |
| **Total** | | **~5s - 15s** | | **Blocks Server** |

### Critical Issues identified:
1.  **Blocking Calls in Async Endpoint**: `service.analyze` is synchronous. Calling it from `async def analyze_text` blocks the entire event loop, preventing the server from handling other requests during the 5-15s analysis.
2.  **Sequential LLM Calls**: The `LLMEngine.optimize` method makes 3 sequential API calls:
    - `_detect_intent`
    - `_optimize_accuracy` / `_optimize_natural`
    - `_extract_corrections`
3.  **No Latency Visibility**: The breakdown of time spent in each stage is calculated in `AnalysisPipeline` but **discarded** before reaching the API response.

---

## 2. Implementation Plan

I propose a 2-phase approach: **Visibility** (to measure exact times) and **Optimization** (to fix the bottlenecks).

### Phase 1: Visibility & Monitoring (Immediate)
*Goal: Expose the `stage_times` currently hidden in the pipeline to the API response for accurate measurement.*

1.  **Update Schema**: Add `stage_times: Dict[str, int]` to `AnalyzeResponse` in `backend/schemas/analysis.py`.
2.  **Update Service**: Pass the timing data from `PipelineResult` to `AnalyzeResponse` in `backend/services/analysis_service.py`.
3.  **Add Logging**: Log the duration of each stage in `AnalysisService` for server-side monitoring.

### Phase 2: Performance Optimization (Async Refactor)
*Goal: Reduce latency and prevent blocking.*

1.  **Make Pipeline Async**:
    - Convert `AnalysisPipeline.analyze` to `async def`.
    - Wrap CPU-bound tasks (Rule Engine, Preprocessing) in `asyncio.to_thread` (or `run_in_executor`) to unblock the event loop.
2.  **Optimize LLM Engine**:
    - Switch to **Async ZhipuAI Client** (or use `httpx`/`aiohttp` if the SDK doesn't support async).
    - **Parallel Execution**: Run `detect_intent` and `optimize` in parallel where possible (or combine prompts).
    - **Prompt Engineering**: Combine "Optimize" and "Extract Corrections" into a single LLM call to reduce round-trips from 3 to 1 or 2.

## 3. Recommended Action

I recommend we start with **Phase 1** to get immediate visibility into the latency breakdown, and then proceed to **Phase 2** to fix the blocking issues.
